# UI memory

- Desktop is a management workspace with a customer preview.
- Mobile/tablet at 1100 CSS pixels or less opens to Dashboard. A top-right hamburger opens a right-side navigation drawer, and Menu Studio is a separate view.
- Menu Studio Photo editor retains the customer-shaped two-column photo menu with owner controls layered on top. Its Availability view uses tall, Messenger-inspired touch rows with larger round images, item names and right-aligned Available/Out of stock controls. Availability view omits prices and option notes and is not a customer layout.
- Do not turn mobile into a compressed desktop table or an ornate restaurant landing page.
- Use the same site and domain for responsive layouts; no mobile redirect or separate mobile site.
- Preserve DM Sans / Manrope. The approved interface direction is neutral-first: near-black navigation, white surfaces and a restrained gray scale. Teal/cyan is a complementary brand color used for primary actions, active navigation, selection, focus and small live-state accents—not large backgrounds.
- Shared Webflow-like color variables live in `dist/theme.css`. Change the neutral scale or `--brand-400`/`--brand-500`/`--brand-600` there before adding route-specific color literals.
- Canonical transparent brand assets live in `dist/assets/brand/`: `qrk-mark.png` for favicon/icon use, `qrk-wordmark.png` for text-only use, and `qrk-logo.png` for the combined lockup. They are cleaned extractions of the approved generated artwork; do not replace them with hand-drawn approximations.
- Dish tiles prioritize photo, name and PHP price. Descriptions remain editable but are not shown on compact tiles.
- Photo editor mode omits the restaurant identity header. Customer preview restores that header and hides item edit, availability and add controls, but this is not an authorization boundary.
- Mobile/customer category tabs jump to menu sections and follow scrolling. Empty categories appear for owners but not customers. Desktop management retains its `All items` filter.
- Responsive Menu Studio category tabs keep their natural left-to-right alignment while the active tab is fully visible. They recenter the active tab only after it becomes clipped or moves outside the visible horizontal strip.
- Preserve item/category creation, item editing/deletion, availability, menu rename and photo selection/removal flows.
- Desktop now opens to a balanced Business Dashboard overview with routes for Business profile, Menu Studio, Staff access, Orders and Settings.
- Phone/tablet opens to the responsive Dashboard; the navigation drawer switches to the separate Menu Studio and back to Dashboard.
- Shared workspace headers do not show the centered Quick/Table demo badge. Dashboard, Orders, and Menu Studio use the same light responsive business/page breadcrumb and outlined hamburger; customer-route service labels remain available where they explain the ordering mode.
- Business profile/QR, staff permissions, live/history orders, sales and settings are clearly UI-only demo states.
- Menu Studio adds category reordering, plain-text option notes and Available/Sold out/Hidden states. Hidden items remain owner-visible and are omitted from customer previews.
- The public development `/menu/` route preserves the simple two-column photo menu without owner controls or a Development badge. It now includes customer ordering, cart, checkout, confirmation and tracking UI; its menu data is not connected to Menu Studio edits.
- Customer order confirmation is a centered popup containing only `ORDER SENT`, `ORDER NUMBER`, and the large bold identifier. It dismisses through the backdrop or Escape; customer-facing verification, status tracking, and confirmation buttons are removed.
- The customer route no longer has a global header/navbar. Table mode now opens with a focused session-entry dialog for name, table, guest count and package as required by the saved preset, followed by a staff/host waiting state. Category navigation remains because it navigates the menu itself rather than the wider product.
- Kusina customer links show QRK Quick. Salamat customer links show QRK Table, derive a fixed demo table from `?table=`, and remove pickup from that visit. This is a mode-aware UI demonstration, not a persistent table session.
- Staff order operations have no Preparing stage. All live orders remain under Received and use one action: Mark paid for Quick or Mark served for Table. Table-mode businesses also retain Tables; Quick businesses show only Received. History remains separate, and the secondary detail panel retains accessible cancellation confirmation.
- The signed-in profile block at the bottom of the sidebar/mobile drawer opens an account menu with Settings and Log out. Staff Settings is a personal account summary; business Settings remains admin-only.
- In the mobile/tablet drawer, the signed-in profile block stays pinned inside the visible bottom safe area while navigation and the UI-preview note scroll independently.
- `AGENT/STYLE.md` is the authoritative visual guide. Business Settings is one heading-free compact rounded list with four stacked full-row actions—Account, Orders, Availability, and Security & sessions—using outline icons, subtle dividers, and chevrons. Details appear only after selection; do not split these rows into separate bordered cards.
- Local preview staff creation generates a one-time temporary password and displays a copyable credential handoff. Any account context marked for first-login password change—including future client admins—is blocked by a mandatory new-password dialog before workspace use. These dynamically created accounts are browser-local until hosted provisioning is connected.
- The Add staff form displays a locked business username prefix beside an editable staff suffix. For Kusina Manila, entering `rhain` previews and creates `kusina.rhain`; staff never type or change the business namespace.
- The business login no longer links to platform administration. `/admin/` is the separate QRK Admin surface with a temporary Continue-to-preview gate, an explicit OAuth-bypass warning, functional Overview/Clients/Client Admins views, client portal creation, initial Client Admin credential handoff, client pause/activation and an Exit preview action. The workflow is browser-local and never exposes Client Staff management.
- Client portals currently customize business identity and logo only. Global QRK colors are authoritative across QRK Admin, Client Admin, Client Staff and customer menus; historical tenant primary/navigation values remain stored for compatibility but do not apply without a future explicit custom-color mode. Do not add tenant-selected fonts or layouts without a new decision.
- QRK Admin Appearance has four dark-sidebar light presets and four full dark presets, plus a global Light/Dark switch. Advanced settings exposes independent 13-token editors for each mode (including badge text). Changes preview live and share across local ports using `qrk_global_theme_v1`; the shared runtime applies the selected mode across QRK Admin, business workspaces and customer menus.
- The public `/landing/` route and focused `/landing/quick.html` and `/landing/table.html` pages preserve the user-supplied cinematic layouts and interactions. Manrope headings and DM Sans body copy align them with QRK, while only their accent colors inherit the global theme; do not simplify or redesign these pages without explicit approval.
- Accent foregrounds are selected by WCAG relative luminance, not a simple brightness threshold. Sidebar child panels and dark dashboard controls must use shared theme tokens; do not reintroduce forced white action text or literal white component backgrounds.
- The experimental `codex/modern-compact-ui` branch uses `dist/modern-compact.css` as a removable final override layer. It preserves QRK assets/colors while testing system UI typography, six-pixel surfaces, flatter elevation and denser dashboard/menu spacing; comparison captures live under `docs/screenshots/modern-compact/`.
- That branch now uses one seamless content plane by default: primary content containers are transparent and borderless, status/help regions use quiet token-derived fills, and glass-like blur is reserved for navigation, sticky category controls and floating actions. This follows Apple's functional-layer approach instead of applying blur to every card.

- The customer cart action is an 85vw floating card without a viewport-wide backing strip. As the footer enters the viewport, the card moves upward and stays 12px above it; footer tracking is immediate with no transition.
- While the customer cart action is visible, the menu reserves the card's measured height plus breathing room so the final item can scroll completely above it; the extra space disappears with an empty cart.
- The public customer route now has explicit device layouts: phone retains the two-column menu and floating order action, tablet uses a wider three-column menu, and desktop uses a broad three-column menu beside a sticky live order summary. Desktop order review expands into a two-column dialog; checkout behavior remains shared across sizes.

- QRK Table staff use a `Tables` tab with six narrow operational cards. Pending requests can be accepted; occupied cards are muted through shared theme tokens and expose `Table cleaned`, which returns the table to Available in the local preview.
- The Tables tab's normal badge counts occupied tables. A separate high-contrast red badge with white text counts pending table and join requests and is hidden at zero; it does not inherit the customizable navigation-badge colors. Table controls rerender only when shared session state changes, keeping cleanup actions and customer session notices stable between polls.

See `docs/UI_AND_FLOWS.md` for detailed behavior and test cases.
