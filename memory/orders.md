# Order operations memory

- Order operations use the shared data-service adapter. Without runtime provider configuration they remain a same-origin/browser demo; hosted staging now has safe GitHub Pages runtime variables and Supabase-backed menus, device registration, customer submission, staff reads, status operations, clear/restore, and Table-session RPCs. Hosted API smoke tests pass for all five tenants; deployed-browser and physical-device evidence remain.
- Hosted staging rejects legacy browser-preview sessions. This prevents an old preview login from silently reading a local order queue while customer orders are reaching Supabase; users must sign in with the hosted tenant account.
- The September 14 order-sync migration adds random browser-installation identity, device-attached order creation, server-side operational clear batches, and restoration of either of the two newest clears. Clearing preserves restaurant, account, staff, menu, product, photo, branding, and destination data.
- Demo orders use a business-scoped localStorage key. Provider-backed orders use the public order RPC and authenticated tenant-scoped staff reads; integer minor-unit money values and unknown order/item fields must remain intact.
- The persisted contract still supports `received`, `preparing`, `ready`, `completed`, and `cancelled`, but staff see every live state under Received. Preparing and Ready are internal compatibility transitions only. Completed and cancelled orders appear in History.
- Staff updates set `updatedAt`, append concise `events` history, save the complete array, and dispatch `qrk:demo-orders-changed`. The dashboard also listens for the browser `storage` event and `qrk-demo-order` compatibility event.
- Live cards expose one mode-aware action: Mark paid for QRK Quick or Mark served for QRK Table. It performs the ordered provider transitions internally and moves the order to History. Cancellation remains in order details and requires confirmation.
- Customer ordering supports search, configured items, quantity, item notes, cart add/edit/remove, table or pickup checkout, order confirmation and tracked status. Cart and the latest active order survive refresh on the same origin/browser.
- Customer menus keep a business-scoped device history of the latest 25 orders for up to 30 days, including order number, time, items, total and current status. Customers can clear only this local history; staff-side orders and any active table session are not deleted.
- Open Tab order IDs are scoped to the current table-session ID. Submitted rounds remain in the active tab and do not enter device history individually. When Tambay staff marks `Customer paid`, the session closes, active rounds complete, and the customer stores one combined table-tab history snapshot. Cancelled, expired, missing, or legacy-cleaned sessions clear the active tab without deleting earlier device history.
- Hosted customer devices restore their own submitted rounds through `list_device_orders`; this device-authenticated RPC is separate from the staff order list and prevents an Open Tab from disappearing after submission on an anonymous phone.
- Kusina's payment-first checkout is a guided second step: Review order ends with `Pay order`, which opens a focused dialog containing only a Back control and two large label-first cards. `💵 Pay at the counter` is enabled; `💳 Cashless` is disabled with a `Soon` badge. Counter orders store device-local `paymentMethod: counter` and `paymentStatus: due_at_counter`. No real payment is executed.
- Desktop order details use a right-side modal drawer. Phone order details use the full usable viewport. Native dialog behavior provides focus containment and Escape close behavior.
- Seed orders are written only when the shared key is absent. Existing customer-written orders take precedence and survive refresh on the same origin/browser.
- Store availability persists as the string `true` or `false` under `qrk_demo_store_open_v1`. Both dashboard status controls update it and dispatch `qrk:demo-store-status-changed`; an open customer tab responds through the browser `storage` event.
- The Salamat customer route loads the local publishable provider config and has been verified to create an order visible in Salamat Admin. Carts and pending idempotency keys are scoped by business slug and data-service mode. Hosted and physical two-device behavior remain unverified.
- Production-intended order creation is a narrow RPC that recalculates published item/option prices, validates availability/selections, uses a per-business idempotency key, generates order/tracking/handoff tokens and stores immutable snapshots. Staff transitions are ordered and tenant-authorized through a separate RPC.
- Customer checkout always sends a UUID idempotency key in provider mode. If an older browser cart has a stale `demo-*` pending request key, checkout replaces only that invalid key with a UUID before retrying and preserves the cart.
- Five centrally defined development clients cover Quick, direct Table, staff-approved Table, open Table tab and staff-approved buffet-package workflows. Normal approved-Table guests may build a cart while waiting but cannot submit it; buffet guests choose a package and wait before menu ordering opens.
- Client Admin/Staff Orders has Received plus a Tables page for Table-mode businesses. Tables supports Available → Request pending → Occupied → Table cleaned → Available. That lifecycle now has a hosted Supabase contract and passed an API-level customer/staff reconciliation check; physical-device browser verification remains.
- LAN pages version the shared table-session module explicitly; the preview server accepts the canonical `clean` table action plus compatible cleanup aliases so stale development tabs do not fail with an unknown-action response.
- If localhost and the LAN address disagree, check for address-specific duplicate listeners on port 4173. On September 13, 2026, an older LAN listener caused cleanup failures until all 4173 listeners were replaced by one current `start:lan` server.
- The September 13 development reset removed all local Supabase order rows while preserving the 8 seeded menu items, and started a fresh version of browser-demo order/session state.
- LAN clients now rewrite the local Supabase loopback URL to the preview computer's hostname, so phones do not incorrectly call their own `127.0.0.1`. Kusina and Salamat development shortcuts authenticate their seeded local Supabase admins; the other three remain explicit preview accounts.
- Every QRK Table customer without a table-specific QR sees a 2×3 Table 1–6 selector. Occupied tables remain clickable with an Open/request-to-join treatment. Table occupancy and join requests are shared by the single LAN preview server; the first guest approves joiners. A `?table=1..6` QR skips manual table selection.
- Table workflows are composed from eight ordered capability layers: table selection, bundle selection, bundle payment, staff acceptance, open order tab, join control, tab payment and staff reopen. Presets enable or skip layers; staff reopen now works in the LAN preview, while payment execution and hosted persistence remain future implementation.
- Confirmation-gated table and join requests show a customer Cancel request action and countdown. They expire after 90 seconds by default (configurable from 30–600 seconds in QRK Admin), release the pending claim and leave the staff queue; this timeout is distinct from active-session expiry.

Authoritative implementation: `dist/index.html`, `dist/app.js`, and `dist/dashboard.css`.
